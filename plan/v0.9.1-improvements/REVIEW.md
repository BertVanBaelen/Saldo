## Findings, by severity

### Blockers (decide before 0.9.1-5 is built)

1. **"Verhoog naar" (and the "Budget toevoegen" prefill) turns a one-month peak into a permanent total.** The user asked for the helper; the problem is the scope of lead decision 14 (raise from the month in view, for good). `SetBudget` writes from `fromMonth` on and deletes the later rows (`ledger/planning.go` SetBudget, 0.8-1; README decision 13). The exit criterion has the user tap "Verhoog naar € 684" in January 2027 for the yearly Familiale verzekering: Overig becomes € 684 for January **and every month after**, so February on plans an extra of € 684 instead of € 288 (+€ 396/month reserved for nothing), and any later row the user had scheduled is silently deleted. This contradicts the user's decision that yearly/quarterly items count only in their month and that reacting is the user's responsibility. Same trap: "Budget toevoegen" prefills `recurring(m) + average` for the month in view (05 "Categories with fixed costs but no budget"), so adding a budget while viewing January bakes € 684 into every month.
   **Change:** for the recurring warning, offer the raise only when the shortfall is not a one-month peak (recurring(m+1) ≥ the current total), or make it "Alleen in januari" = two PUTs (m = X, then m+1 = the old total; both PUTs still delete any rows scheduled after m+1, so re-PUT those or warn); prefill "Budget toevoegen" from the running month's recurring (or the monthly items only), not the month in view. Ask the user which; update the exit criterion and the 05 test "a tap sends PUT … 68400".

### Should fix

2. **Missed occurrences shrink the extra although they are not in the forecast.** A missed occurrence changes no balance (`forecast_project.go:58-62` comment, `:409-413` `continue`, `:627` missedOn items carry no amount into `bal`), yet 04 counts it in `recurring(c, m)` ("paid, late, missed or still to come alike"). The category then gets neither the item nor its share of the total: the forecast reserves less than the total. The plan's own number shows it: W1 November, Krant is missed (TestWorld "W1 missed": `Krant 2026-11-05 -1000`), Boodschappen extra 9000, November end **+1000** for a payment that is not expected. README "Known limits" justifies it with "the cost is planned, paid or not" — that holds for `Need` (`:663-673`) but not for the balance. **Change:** either count only occurrences that are matched, pending, late or still to come (exclude `missed` and "assumed paid" unmatched ones, `:407-408`), keeping `Need` as it is; or keep the rule but ask the user and rewrite the known limit truthfully ("a missed payment frees its part of the total"). Re-derive TestWorldTotal W1 November either way. The plan's W2 case is the same: W2 has no Luminus row and `dataDate` 2026-11-18 (bank sync), so the in-test Energie occurrence of 3 November is missed (`:405-413`, `fcMissed`); its Need (Costs 25000) is right, but the spread reserves 5000 less than the total that month.

3. **"Assumed paid" items double-count in the running month.** An item without counterparty whose payment differs from its amount stays unmatched (`fits` exact amount, `:328`); its occurrence is assumed paid (`:407-408`) and counts in `recurring`, while the payment row is variable spending in its row's category (`:471-485`). If that is the same category, the cost reduces the extra **and** `Rest`. Document under Known limits (Familiale verzekering is exactly this kind of item) or exclude unmatched past occurrences as in 2.

4. **TestWorldTotal's identity check cannot pass as written.** 04 Tests: "With every assignment of the test removed again the forecast equals TestWorld's". The test also adds a Vrije tijd budget 3000 on W1 and an item + budget 25000 on W2, so removing only the assignments still differs (W1 Vrije tijd 3000 budget vs TestWorld `Vrije tijd 0/1000/0 average`, `world_test.go:175`; W2 Energie line). **Change:** compare against the same fixture (budgets and Energie kept) without assignments, or remove the added budgets/items too.

5. **Compile break inside 0.9.1-4.** `planBudget(b)` is a struct conversion (`server/planning_forecast.go:224`, struct `:35-42`); adding `Total`/`Recurring` to `planning.Budget` in step 1 (Opus) breaks `server` until step 3 (Sonnet). Step 1 says "all existing goldens green before writing the new test", but the server goldens cannot compile, and step 1's agent only runs `go test ./internal/planning/...`. **Change:** move the two `planBudget` fields into step 1 (and have it run `go build ./...`).

6. **`average=1` must not touch the golden or the receipt.** `RefCategory` is both the wire shape and the receipt's input (`budget_reference.go:24-28`, `receipt/receipt.go:177-180`). Adding `Average int64 json:"average"` to it changes `testdata/reports_budgets_golden.txt` for every request; `omitempty` drops the "0 when there is none" the plan promises. **Change:** say how: a separate wire type (or `*int64` with `omitempty`) built only when `average=1`; `In()` unchanged.

7. **Sub sheet from inside a breakdown sheet loses state.** `sheet` is a single node (`Overzicht.tsx:690-735`), so opening a sub row's sheet unmounts the Uitgaven sheet; `BdItem`'s expanded state is local `useState` (`OverzichtSheet.tsx:319-321`), so Back returns to a collapsed list and the tapped button no longer exists to take focus back (01 Tests: "focus returns to it when the sheet closes"). **Change:** 01 must say what Back restores (expanded top + focus on that top's chevron, e.g. expanded keys lifted to the page) and test it for a breakdown-sheet sub row, not only the "Per categorie" dropdown (whose `CatItem` stays mounted).

8. **Late occurrence of last month.** A late occurrence dated in the previous month is moved to tomorrow (`:405-406`) and so paid in the running month's balance, but `recurring` goes by `oc.date[:7]`: it counts in no month in view, so the running month's extra does not shrink. Minor; add to Known limits or count late ones by their event date.

9. **0.9.1-5 is too big for one Sonnet agent** (stepper, row rewrite, warnings + Verhoog, assigned-items chevron, "Vaste kosten zonder budget", Zonder categorie list with live preview and PATCH, four text sites, two analysis docs, 6 test files). Split into 5a (stepper, rows, warnings, chevron, prefill) and 5b (Zonder categorie + preview, texts, docs).

10. **File clash with wave 1.** 0.9.1-5 edits `lib/reports.ts` (`BUDGET_NOTE`) and `Overzicht.test.tsx`, owned by 0.9.1-2 / 0.9.1-1; the README lets wave 1 run alongside wave 2. **Change:** state that 0.9.1-5 starts only after wave 1 is merged.

11a. **New required TS fields break the typecheck gate.** `PlanBudget` (`web/src/lib/planning.ts:19-27`) is built as typed literals in the web tests (`rest:` 11 times; `source: 'budget'` in `reports.test.ts`, `Overzicht.test.tsx`, `PlanningInstellenBudget.test.tsx`, …), and recurring-item fixtures in `planningItems.test.ts`, `PlanningInstellen.test.tsx`, `PlanningTerugkerend.test.tsx`, `test/helpers.tsx`. Adding required `total`/`recurring` (0.9.1-4 step 3) or `categoryId` (0.9.1-3 step 5) fails `npm run typecheck` at the lead's phase gate before 0.9.1-5 touches those tests. **Change:** make them optional as `average?` already is (precedent), or give the fixture updates to the step that adds the type.

11. **A user-set € 0 budget is a visible behaviour change.** `SetBudget` accepts 0 (refuses only `< 0`); today such a row with nothing spent vanishes from the forecast and from the editor rows (`:555`, `PlanningInstellenBudget.tsx:122`). The new keep-condition lists it. The "nothing assigned, nothing changes" claim holds for every fixture (grep: no zero budget in any test), but it is a change in production (a good one). Name it in the CHANGELOG/known behaviour and add one engine test (budget 0, no spend, nothing assigned → listed, plan 0).
