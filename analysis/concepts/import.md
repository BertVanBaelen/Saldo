# Import batch (CSV, Bilance)

Analysis: 4.1 (CSV fallback), 4.6, risks 1, 10, 11 · Data: `import_batch`, `category_mapping` · Screens: [importeren](../screens/importeren.md) · Phases: [0.1-7](../../plan/v0.1-mockup/07-missing-designs.md), [0.3-6](../../plan/v0.3-bank-sync/06-csv-import.md), [0.5-1](../../plan/v0.5-bilance-import/01-spike-bilance-csv.md), [0.5-2](../../plan/v0.5-bilance-import/02-import-wizard.md), [0.5-3](../../plan/v0.5-bilance-import/03-category-mapping.md), [0.5-4](../../plan/v0.5-bilance-import/04-overlap-and-duplicates.md), [0.5-5](../../plan/v0.5-bilance-import/05-batches-and-undo.md), [0.5-6](../../plan/v0.5-bilance-import/06-learning-and-backfill.md)

## Wizard steps
1. Pick the file (CSV; Bilance export uses a saved "Bilance" preset).
2. Map columns: date, amount, counterparty, communication, category, account. Choose the target account.
3. **Category mapping**: every distinct source category with its transaction count and total. Per category: map to an existing category (name-similarity suggestion), create new, merge several into one, or leave uncategorised. The Bilance export has two columns, `Categorie` and `Subcategorie` (spike S2), so a source category is that pair, stored as two parts and never as one joined string (names contain commas, ampersands and ` / `). It maps on the pair by default, "map by parent" maps all subcategories of one `Categorie` at once.
4. Preview with **probable duplicates** (booking date ±1 day, same amount, similar counterparty), skipped by default and shown side by side, with a choice to import one anyway. Suggested **import cutoff** per target account = first synced date of that account; rows dated on or after it are skipped. Both apply to a Bilance file only (0.5-4). For a skipped duplicate the source category is applied to the existing transaction if it is uncategorised.
5. Result with **undo** ("Ongedaan maken"; the same on every entry of the history).

## Rules
- Every import is a **batch** that can be undone as a whole. Re-importing the same file creates no duplicates (dedupe key, file hash).
- 0.3 duplicate rule: a row equal in booking date, amount, counterparty and communication to a booked row the account already holds (any source) is not stored again, counted per occurrence. The same exact match applies in the sync to a bank row that equals an imported row. The fuzzy rule and the cutoff (0.5-4) are for a Bilance file at import only: the generic CSV import is also the fallback after a failed sync, which a cutoff would block, and the sync keeps the exact rule, since a fuzzy match there could merge two real payments of one amount a day apart.
- **Overlap and duplicates** (0.5-4, Bilance files only): per target account the rows on or after the cutoff are skipped first and counted (*na afkapdatum*; the cutoff is the first synced booking date of the account, suggested and editable, or none). The rows left are matched with the stored booked rows: an exact match (0.3 rule) is dropped; a fuzzy match (same amount, at most one day apart, similar counterparty; a stored row matches at most one incoming row) is a **probable duplicate**: listed side by side in the preview, skipped unless the user includes it. A skipped duplicate hands the file's category (through the mapping) to the stored row when that row has no category and is not split (origin `import`, same transaction, counted as *categorie overgenomen*); a manual, rule, suggestion or earlier import category is never overwritten. The taken-over categories are writes on existing transactions, not part of the new batch. See [docs/api.md](../../docs/api.md), "Overlap and duplicates".
- **Undo** (0.5-5): a batch is undone as a whole, in one database transaction: the transactions with its id are deleted (splits and "is a transfer" overrides cascade; notes and categories go with the row), `undone_at` is set and the batch stays in the history. Manual and synced transactions are never touched. Undo removes **all** the batch's rows, also the ones the user changed afterwards (the point is to reverse the whole import), so the confirmation counts first: how many rows go and how many of them the user changed (`changed` = a category set by hand or by a suggestion, or a split; a rule's category and a note are not counted, see [docs/api.md](../../docs/api.md), "Undo"). Stays: categories the import created, categories handed to existing transactions (0.5-4, outside the batch) and the saved mapping. One file over several accounts is one **run** of batches (same file hash, creator and creation second, no new column); the history shows a run as one entry with "Alles ongedaan maken", which undoes every batch of it or none. A batch that brought nothing (the same file again) stays in the history, muted as "Niets nieuws toegevoegd", without undo. After an undo the same file imports again in full. Suggestions are computed on read from the rows that exist, so those of an undone batch vanish with it.
- Mappings are saved per user and source and reused; changing a mapping can be re-applied to that import (API, 0.5-3).
- **Category mapping** (0.5-3): per pair a choice of map to an existing category, create a new one (a subcategory of a main category, or a main category, with an icon), or leave uncategorised; several pairs mapped to one category are the merge. A name-similarity suggestion and the saved target are pre-selected and labelled (Voorstel, Opgeslagen), never applied unseen. New categories are made in the transaction of the import. Imported rows get the category with origin `import`; an unmapped pair never blocks the import and leaves its rows uncategorised. The two parts of the pair are kept on each imported row so a re-apply rewrites only rows of origin `import` (and still-uncategorised rows of a skipped pair) of that batch, never a manual, rule or suggestion category. See [docs/api.md](../../docs/api.md), "Category mapping".
- Mapped imported categories feed the learning ([categorisation-rule](categorisation-rule.md)).
- Bilance CSV layout: read from one real export in spike S2, the category format included ([0.5-1](../../plan/v0.5-bilance-import/01-spike-bilance-csv.md)). Incomes, amounts of 1 000 or more and transfers between own accounts were not in the sample and stay **[verify]**: the parser reads what it can without guessing and makes anything else an unreadable row.
- **Accounts from a column** (0.5-2): the Bilance column `Rekening(en)` holds the *name* of an account, not an IBAN. The wizard lists each distinct name and maps it to one of the user's accounts (edit permission); an unmapped name blocks the import. One batch per account. The IBAN guard of 0.3-6 does not apply to such a file.
- **Personal data in a Bilance row:** the card payment string in `Betalingskenmerk` carries the card holder's name and a masked card number. Only merchant, date and place are kept as the communication; the rest stays in the raw row, which no screen or API shows.
- **Limits** (since 0.5-2): 20 MiB and 100 000 rows per file (0.3-6: 5 MiB and 20 000).
- The full Bilance import comes **before planning** (decision 3 Nov 2026), so the forecast can find quarterly and yearly items in 12+ months of history.
