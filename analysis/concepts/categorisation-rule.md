## Rules
- A rule matches on counterparty name or IBAN, communication (contains, or an RE2 regex) and amount range, with a priority. Conditions are ANDed, at least one. Text is compared normalised (lower case, Latin diacritics folded, white space collapsed); the regex runs on the communication with white space collapsed, not folded. The amount range is on the **absolute** amount, inclusive.
- Limits: counterparty 140 characters, communication 200, priority 0 to 1000, 200 rules per owner.
- Owner: an **account** (shared by members with edit access) or a **user**.
- **Which rules apply** to a transaction: the rules of its account, plus the member's user rules only when the account has exactly one member. A user rule never applies to a shared account (0.6-1 adds "convert my user rules to account rules" for a personal account that gets a second member).
- **Evaluation order**: priority DESC, then newest first. A higher priority wins, a tie goes to the newest rule.
- **Reordering** (0.4-4): the list position is the priority order, top first. Moving a rule sends the new order of every rule you can edit, and the server renumbers their priorities so they are distinct and follow the list (distinct values stay as they are, ties such as the default 0 are broken, down to 0 at the bottom). Read-only rules (an account where you only have Lezen) keep their priority, so they may end up in another place among the reordered ones; another user's rules are never touched. The same order again changes nothing.
- **Origin**: every transaction has one category, the same for every member of its account, with an origin: `manual`, `rule`, `suggestion` or `import`.
- **Precedence**: manual choice > highest-priority matching rule > learned suggestion. `import` (a category from a Bilance import) is protected like a manual one. Automatic writers only change a transaction without split parts that has no category or origin `rule` or `suggestion`, so re-running rules **never overwrites a manual or imported choice**.
- **No auto-apply**: creating, changing or deleting a rule does not run it. Rules run on new transactions (sync, CSV import) and on demand. Deleting a rule keeps the categories it set. A transaction that no rule matches any more keeps its category.
- **Live preview** (0.4-4): the rule editor shows "Past op N transacties" while you type, and how many of those would change category. It counts only your own rows (pending too) in the rule's scope (an account rule: that account; a user rule: every account where you are the only member and may edit), through the same matcher as the engine, and the draft competes with the owner's other rules as if it were stored. Rows that match but would stay as they are are counted apart (manual, import, split, other rule). It writes nothing; applying the stored rule afterwards changes exactly the previewed number of rows when nothing changed meanwhile.
- **Apply one rule on demand** (0.4-4): runs only that rule over its scope with the same guards as "apply to similar" (a manual, imported or split row never changes, a row that another rule outranks keeps what it has). The answer says how many rows changed and how many were skipped, and why. Running it again changes nothing.
- **Learning**: map a counterparty to its most frequent category, with a confidence level. Low confidence is shown for confirmation, never applied silently. The v0.4 version is the simple one described under Suggestions below; 0.5-6 extends it (new rows, backfill, Bilance history).
- Manual override offers "apply to similar transactions and create a rule" ("Toepassen op vergelijkbare en regel maken"). It sets the picked category manually on that row, then creates a rule "counterparty contains" the row's counterparty name (priority 0) and applies it to the stored transactions it matches. The rule is a user rule when the row's account has exactly one member (it covers every account where the user is the only member and may edit), an account rule of that account otherwise. If the owner already has a rule whose only condition is that counterparty, that rule gets the new category instead of a duplicate. A row without a counterparty name has no basis, so the option is not offered.
- "Apply to similar" changes only rows with no category or origin `rule` or `suggestion`. It never overwrites a `manual` or `import` category or a split, nor a row that another rule outranks. The answer says how many rows changed and how many matching rows were skipped, and why (manual, import, split, other rule). There is no undo of the bulk change: pick the right category again with the option on, the same rule is reused and the rows follow.
- **Suggestions** (0.4-4, before 0.5-6): for a counterparty you categorised before, the category you chose most often, offered for the rows of that counterparty that still wait for a category. Computed on every read from your own data; nothing of another user is used.
  - Training rows: your rows (accounts you hold, read-only too) without split parts, with a category of origin `manual` or `import` and a counterparty name. Categories set by a rule or a suggestion are echoes and do not count.
  - Per counterparty (the name normalised like rule text) the category with most rows wins (a tie: the newest row). Confidence = round(100 × the winner's rows / rows seen). Offered when seen ≥ 2, confidence ≥ 40 and at least one open row (no category, no split, on an account you may edit). Only the winning category is offered.
  - Nothing is applied automatically. "Bevestigen" gives the rows that wait now the category with origin `suggestion`, and never replaces a rule's or a manual category. It does not cover rows that arrive later: automation for future rows is a rule ("Als regel") or, later, 0.5-6. "Negeren" dismisses it.
  - Only the decisions are stored (confirmed or dismissed, per user, counterparty and category); open suggestions are computed and never stored. A confirmed or dismissed suggestion does not come back.
- Learning improves after the Bilance import, which now comes right after categorisation, so rules carry the load only briefly.

## In the design
- Start alert (green): tag icon, "4 transacties te categoriseren", links to Transacties filtered on "Niet gecategoriseerd". Desktop sidebar shows a count badge "4" on Transacties.
- Categorieën en regels (mockup `categorieen.html`): tree, rules by priority with an editor and live preview, suggestions with confidence ([categorieen](../screens/categorieen.md)).
- Meer: "Categorieën en regels · 3 suggesties om te bevestigen".
- Notification type "Te categoriseren": at most once a day at 19:00.
- Transacties detail: checkbox "Toepassen op vergelijkbare en regel maken" with "Ook N andere transacties van X krijgen deze categorie." (or "Nieuwe transacties van X krijgen deze categorie."), unchecked each time; toast "Regel gemaakt · N andere bijgewerkt". The "Niet gecategoriseerd" filter chip carries the count. Built differently: N counts only the rows that change (skipped rows are reported apart), and when the rule already exists it is reused, so "Regel gemaakt" does not fit that case (wording to settle in 0.4-3).
