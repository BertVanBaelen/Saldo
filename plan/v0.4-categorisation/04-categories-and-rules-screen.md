## Goal
See and manage all categories and rules in one place.

## Steps
1. Category tree editor as designed.
2. Rules list with priority (reorder), owner and conditions; the rule editor with a live preview; edit and delete.
3. Simple suggestions from history (counterparty → most frequent category, with confidence) in `category_suggestion`; low confidence only for confirmation; "N suggesties om te bevestigen" in Meer. Full learning follows in 0.5-6.

## Done when
Every rule can be found, changed and reordered, and suggestions can be confirmed or dismissed for good.

## Notes from 0.4-1 and 0.4-2 (10 Nov 2026)
- **Built in 0.4-4:** the reorder and the live preview of a rule, planned here as server work, exist now (see "Built" below). The planned reorder, a permutation of the `priority` values among the viewer's visible rules, became a renumbering of the rules the viewer can edit (Decisions 3).
- **Suggestions** must write through `categorise.Assign` with origin `suggestion`: it never replaces a rule's or a manual category. Built that way (Decisions 2).
- **Names with punctuation:** Bilance names contain commas and `&` (`Energie, nutsvoorzieningen`, `Eten & Drinken`). No UI or CSV code may split a category name on commas. For the 0.5-3 mapping, store the source path as two parts (top and sub), not one joined string, because a name may contain any punctuation, ` / ` included.

## Decisions (10 Nov 2026)
1. **Suggestions are computed on read; only decisions are stored.** `GET /api/suggestions` derives them from your own rows and writes nothing. Training rows are your rows with a category of origin `manual` or `import` (a rule's or a suggestion's category is an echo and does not train); a suggestion needs `MinSeen` 2 and `MinConfidence` 40 (constants in `categorise`). Only `confirmed` and `dismissed` are stored, per user, in `category_suggestions`; `open` is never written. A confirmed or dismissed suggestion never comes back for that counterparty and category.
2. **Confirming categorises the rows that wait now and also makes the rule for new ones** (changed after the first test, Decision 11). The write goes through `Assign` with origin `suggestion` and never replaces a rule's, a manual, an imported or a split row's category. Rows that arrive later get the category from that rule on your personal accounts; learning for the rest stays 0.5-6. A second confirm answers `200 {"updated": 0, "rule": null}`, a second dismiss `204`.
3. **Reorder renumbers the rules you can edit.** The request names exactly those rules, top first; their priorities become distinct values, `v` being the old values from high to low (`v_0 ≥ v_1 ≥ …`, n rules). Built: `p_0 = max(v_0, n−1)` and `p_i = max(n−1−i, min(v_i, p_(i−1)−1))`. Planned: the same `p_0` and `p_i = min(v_i, p_(i−1)−1)`, which goes negative on low ties (for `v = [5, 0, 0]` it gives 5, 0, −1; the built formula gives 5, 1, 0). The two are identical for distinct values, and the built one never goes below 0, hence the floor `n−1−i`. Ties (such as several rules at the default 0) are broken, down to 0 at the bottom. Read-only rules keep their priority; another user's rules are never touched.
4. **The preview needs edit permission on the account** (a read-only account answers `403`), counts only your own rows and runs the same engine as "apply to similar" and `POST /api/rules/{id}/apply`, so applying the stored rule afterwards changes exactly the rows the preview announced. A preview that names `ruleId` and leaves out `counterpartyIban` uses the stored rule's IBAN, because the editor only has it masked.
5. **Amounts are compared without sign**, in the rule, the preview and the apply. The editor's help text says so ("Zonder teken: Saldo vergelijkt met het bedrag zonder plus of min, voor uitgaven en inkomsten."), which differs from the mockup's ("Bij een uitgavencategorie kijkt Saldo naar uitgaven, bij een inkomstencategorie naar inkomsten."). See open question 1.
6. **Removing a category with "Niet gecategoriseerd" deletes every user's rules for it**, as the server did from 0.4-1; the removal editor's note counts only the rules you can see and reads "Je N regels kiezen X. Die regel wordt verwijderd." (or "Je 1 regel kiest X. Die kiest voortaan Y." when the transactions move to a category Y). See open question 5.
7. **"Als regel" opens the rule editor filled in** for a user rule on the suggestion's counterparty with "is gelijk aan" (as the mockup said), the suggestion's category and "Ook toepassen op bestaande transacties" ticked, so you can adjust it (bevat, an amount range) before saving. A user rule applies to your personal accounts only. See open question 3.
8. **Deviations from the mockup:** the per-rule "Past op N transacties" is shown in the editor only; a new rule has no position select (move it afterwards with the arrows); the owner of a rule cannot change while editing (the server refuses; make a new rule); no hash deep links such as `#regel-3`, query parameters instead; the footnote under the category tree reads "Overschrijvingen tussen je eigen rekeningen herkent Saldo zelf: ze tellen niet mee als uitgave of inkomst. Wat naar een spaarrekening gaat, telt als gespaard." instead of the mockup's "… krijgen geen categorie …", because a transfer may get a category from a rule or a pick (decision of 10 Nov 2026) and sums treat transfers at query time, not by category; the browser's native selects are replaced by one shared dropdown component (`web/src/components/Select.tsx`: a button that opens a list under the field, with the arrow keys, Home, End, Enter and Escape), at the user's request after testing, where the mockup used native selects in a styled frame; the toast after "Bevestigen" has a link "Regel openen" (to `?tab=regels&regel=<id>`), where the mockup's toasts are text only.
11. **"Bevestigen" makes a rule** (10 Nov 2026, after the user tested the app and expected a rule under Regels). In the one database transaction of `POST /api/suggestions/confirm`, after the rows that wait are categorised, `confirmRule` (`server/internal/ledger/suggestions.go`) makes sure the viewer has a user rule (no account, as "apply to similar" makes for a personal account) "counterparty is equal to" the suggestion's counterparty, with the suggestion's category. It reuses `counterpartyRule`, the lookup `similarRule` uses ("bevat" and "is gelijk aan" both count), and the one rule creation path `createRule`; the rule is not run, because the confirm just categorised the rows that waited. The answer is `{"updated": 3, "rule": {"id": 12, "created": true, "conflict": false}}`; `rule` is `null` for a repeated confirm and for a counterparty name that rule text cannot hold. An equivalent rule is reused (`created: false`). A rule of the viewer for that counterparty with another category is never changed: `conflict: true`, no new rule, the waiting rows are still categorised, and the toast says that rule stays. At the limit of 200 rules per owner the creation fails and so does the whole confirm, with nothing stored. A user rule applies to personal accounts only (Decision 7), so a suggestion built from the rows of a shared account categorises those rows but its rule will not reach that account (open question 3).

## Not built here
- The per-rule "Past op N transacties" in the rules list (one preview request per rule): the editor shows it for the rule being edited.
- A position select on a new rule: it gets priority 0 (it wins ties against older rules at 0) and is moved afterwards with the arrows or the position select of its editor.
- Confidence on the suggestion strip in the Transacties detail: 0.5-6.
- Learning and backfill (0.5-6): rows that arrive later now get a rule's category on personal accounts, because "Bevestigen" makes a rule (Decision 11); what stays for 0.5-6 is learning for rows no rule covers, shared accounts included, and the backfill.

## Open questions for the user
1. **Amount direction.** Rules compare the absolute amount, so an expense rule "Bedrag tussen € 20 en € 200" also catches a € 50 refund from the same counterparty. Recommendation: with an amount condition, match only rows whose sign fits the category's type (an expense category only money out, an income category only money in), and say so in the help text as the mockup did.
2. **Preview of an existing rule with an IBAN.** Resolved (10 Nov 2026): built as recommended. When `ruleId` is sent and `counterpartyIban` is left out, the server uses the stored IBAN, so the preview of such a rule no longer asks to retype it (the field says "Saldo toont een IBAN nooit voluit. Laat het staan om het te houden.").
3. **"Als regel", "Bevestigen" and shared accounts.** A suggestion can come from rows of a shared account, but "Als regel" and "Bevestigen" both make a user rule, which never applies to an account with more than one member; "Bevestigen" categorises those rows, but its rule will not reach that account. Recommendation: add the account (or accounts) of the open rows to a suggestion, so "Als regel" can preselect that account's rule, and "Bevestigen" can make that account rule.
4. **Text of the apply box.** Resolved (10 Nov 2026): the box now reads "(handmatige keuzes, imports en splitsingen blijven staan)"; the toast after saving still names what stayed.
5. **Removal and other users' rules.** "Niet gecategoriseerd" deletes every user's rules for the category, while the note counts only the rules you can see. Half settled: the note now says "Je N regels kiezen …". Still open: it does not say that rules of other users for this category go too. Recommendation: add that, without a number, like the line about their transactions.
