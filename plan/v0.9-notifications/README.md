# Version 0.9 · Notifications

**After this version you can** get a push notification on your Android phone or iPhone, or an e-mail, when an account is heading into its buffer or below zero, when a bank link expires or a sync stops (also when the link that feeds a shared account is someone else's), when someone joins or is invited to a shared account, when a new device signs in, when a contribution is missing and when new bank transactions wait to be categorised. If you switch them on, a **week overview** (Sunday 19:00) and a **month overview** (last day of the month, 19:00) show where your money went, as a receipt that prints in the app. You choose per type and channel, with quiet hours.

Status: **released as 0.9.0** (25 Nov 2026; built on branch `v0.9-notifications`), unit-tested by the builders and the lead's full gate; not yet tested on real phones or in real mail clients (0.9-5). Refined 18 Nov 2026 against the code of 0.8 in progress (the overview receipt, 0.9-3c to 0.9-3e, added 23 Nov 2026); built 23-25 Nov 2026. Analysis section: 4.9. Roadmap: [../README.md](../README.md).

## Decisions (18 Nov 2026: the user's answers and the facts found in the code)

**The user's answers**
1. **Timing.** After the nightly sync (04:00 and later) the planning warnings go out at **07:00** for both channels, the morning after the forecast changes. A push that falls due inside quiet hours **waits** until they end and is not lost. Quiet hours stay a plain on/off switch with fixed 22:00–07:00 (Europe/Brussels), as in the mockup; security messages ignore them.
2. **Repeats.** One planning message per account per morning, the **worst** state first (red before buffer); the milder one that is still true follows on a later morning, each key once. When an account is back to ok for a month the log row is cleared (**re-arm**), so a new dip for the same month notifies again. A red month that improves to buffer within the same month is silent.
3. **Lock screen.** A web push cannot hide its text (the OS decides, risk 14). The spike (0.9-2 last step) runs as soon as a bare push arrives on both phones. Until it says otherwise every push uses **generic text** (no account names, no amounts); one payload builder with two levels (`generic`, `full`) so the outcome is a one-line switch, tested for both. The board's amount pill, account names and expandable chart are built **only** if the spike shows the lock screen can hide them (see known limits).
4. **First run.** The first time each trigger runs, its current state is written to the log **without sending**: every account that is already red or in the buffer, the existing e-mail reminders copied to the push channel, the open join notices and invitations, the missing contributions of the running month, the digest high-water mark. One baseline marker per trigger in `notify_runs` (`baseline:planning`, `baseline:joined`, ...), so a trigger that lands in a later phase baselines itself and never sends pre-upgrade state. Only changes after that notify.
5. **Recipients.** "Koppeling verloopt" and "Synchronisatie gestopt" go to the connection's owner **and** to the manager of a shared account that the lapsed link feeds when no other healthy source covers it (risk 5b). "Iemand sluit aan" goes to the manager. The invited user gets a **push** for an invitation. Left, manager changed, account deleted and rules notices stay in-app only.
6. **"Bijdrage ontbreekt"** stays in 0.9 (default off/off): on the 3rd, to the member who owes (own reminder) and to the manager (who is behind). Members already see each other's `received` on the Bijdragen card, so nothing new is exposed.
7. **"Te categoriseren"** (19:00, only if there is something) counts **new bank-synced rows** since the last digest that are still uncategorised; Bilance and CSV imports and the old backlog never trigger it; the push says the count only, no merchant names.
8. **Real-phone tests** run on the live add-on: install `0.9.0-dev` after a Home Assistant backup (as for 0.3). Real domain, real VAPID key, real phones; subscriptions stay valid into the release because the origin does not change. This is a **deliberate exception** to "never deploy a dev build to the live add-on" (0.8 real-data check): the build is the **whole 0.9.0-dev** on top of the released 0.8.1 (user decision 23 Nov 2026: "just develop, then I test it live"; there is no separate spike build), and **rollback means restoring the backup**, because migrations 0018 and 0019 rebuild tables. Push text is generic by default (decision 3), so what the lock-screen spike finds is a one-line switch afterwards. Migrations may still change until the first live install of the dev build; after that an applied migration is never edited, a new one is added.

**Decided by the lead (say if you want it otherwise)**
8b. **The invitation is a type of its own** (`invite`, "Uitnodiging voor een gedeelde rekening", group Gedeeld, push on and **e-mail on**, with an e-mail template): your answer was "a push"; the e-mail default and template are the lead's choice, so the Meldingen screen can show a chip pair like every other type. Say if the e-mail should default off.
9. **Type keys are pinned**: `rood`, `buffer`, `consent`, `stop`, `joined`, `invite`, `contrib`, `cat`, `device`, `week`, `month`. The mockup's `toestel` becomes `device`; the alert types of `GET /api/alerts` (`planning`, `sync`, `categorise`, …) are another namespace. One defaults table in Go (`notify.Types`) serves the API and the sender; the sender today treats a missing row as "on", which is wrong for `buffer`, `cat` and `contrib` (e-mail off).
10. **Our own Web Push sender on the standard library** (RFC 8030/8291/8292, tested against the RFC test vectors), no new dependency: the repository vendors UI code by hand for the same reason, and the SSRF guard needs control of the HTTP client anyway. If you prefer `webpush-go` (MIT) it replaces one file.
11. **Push is a channel, not a second system.** One dispatcher (`notify`) takes a typed message for a user and delivers it to the channels they chose, claiming the log row before sending and removing the claim when the send fails (retry on the next run). `CheckConnections` of 0.3-2 becomes one of its triggers.
12. **The forecast rule moves out of the server layer.** `accountPlanningAlerts` and its helpers live in package `server` today; the scheduler cannot import them. The month-end red/buffer rule (decision 14 of 0.8) moves to `planning` (data: month, end, low point, red-from date, cause, buffer); Start maps it to `ledger.Alert`, 0.9-3 to messages. One rule, two renderers.
13. **Four e-mails have no design**: "Te categoriseren", "Bijdrage ontbreekt" (member and manager variants), "Uitnodiging voor een gedeelde rekening", and the manager variants of the two bank mails. They are built in the existing layout; the user checks them once in the preview (0.9-1 step 6).
14. **UI libraries** (user, 18 Nov 2026: "keep Kokonut and Untitled UI in mind"): the 0.8-5a decision is extended to the Meldingen screen. `web/src/ui` already has `Switch`, `SegmentedControl` and `Badge`; the push/e-mail chips are built on React Aria's `ToggleButton` (already a dependency), restyled; no new package. Existing screens stay untouched.

**The week and month overview (user, 23 Nov 2026: "add a notification for a week overview and a month overview; use the receipt printer component from Kokonut UI to show the categories, prices and subcategories"). Decisions 15 and 16 are the user's answers and request; 17 to 19 are the lead's calls (say if you want them otherwise).**
15. **Two new types, `week` (Weekoverzicht) and `month` (Maandoverzicht)**, group Overzicht. Answers: they go out **Sunday 19:00** (the week Monday to Sunday that is ending) and **19:00 on the last day of the month**; **one overview per user over all their current accounts** (Alles, "ter info"; the page can switch to Persoonlijk or Gedeeld); **both opt-in** (push and e-mail off until switched on, against the lead's proposal of week push on, month push and e-mail on); the receipt carries a **comparison with the previous period** and, for months, **each category against its budget**. Not chosen: the outlook line (the planning warnings say that). Built in 0.9-3c (data), 0.9-3d (screen), 0.9-3e (notifications).
16. **The animated receipt is on one in-app page only.** Kokonut UI's Receipt Printer (kokonutui.com, MIT) is vendored and adapted for `/overzicht/bon/...` (0.9-3d). A web push cannot render React and an e-mail cannot animate, so the push stays generic and the e-mail carries a **static** receipt block. This **extends the 0.8-5a decision** by name: Kokonut was limited to small motion touches on Planning; the printer is a user request, for this page, and opens no door to other components or existing screens.
17. **(lead)** **The comparison runs against the previous full period even while the period is running** (the 19:00 message is a running period; Overzicht gives a running period no trend and keeps doing so). The receipt says "Loopt nog, tot zo 22 nov" because today's bank rows are not booked yet; pending rows never count, as everywhere.
18. **(lead)** **The model is built in Go behind one route** (`GET /api/reports/receipt`), because the e-mail is server-side; the page renders the same model. The roll-up, order, trend and budget rules therefore exist in Go and in Overzicht's TypeScript; a cross-check golden (October of the demo) pins them together. Weeks reuse `reportBucket`; only the grouping differs (`ReportRange`). Computed on read, nothing stored.
19. **Decided by the lead**: ISO weeks (Monday to Sunday, Brussels, the ISO week-year); an empty period sends nothing; a first period the history only partly covers says "vanaf <datum>" and has no comparison; an account that is failing or stale makes the receipt say "Niet volledig: …"; both overviews of a month end that is a Sunday go out as two pushes; `Expires` after 3 days, a catch-up after 22:00 waits for 07:00; the first run marks a period whose 19:00 has passed as suppressed; no pending line and no per-account block (a question for the user if the snapshot misleads).

## What the code showed (corrections to the old plan)
- **Outbound traffic grows.** The security baseline says the only outbound hosts are Enable Banking and SMTP. A push endpoint is a URL the browser supplies: https only, a push-service host allowlist, no redirects, timeout and size cap (0.9-2). The baseline, `docs/architecture.md` and the 1.0-2 review line change with it.
- **`push_subscriptions.device_id … ON DELETE SET NULL` is a privacy bug.** A signed-out device would keep receiving pushes. Subscriptions are deleted on sign-out, sign-out-others, password change and the 90-day idle expiry (0.9-2, migration 0018).
- **The log cannot guarantee "once".** `notification_log` has a lookup index only; repeat protection today is the service mutex and a read-then-write. A unique key per user, channel and message closes it (0.9-3).
- **`jobs.Scheduler` only knows intervals.** "07:00" and "19:00" are wall-clock decisions: the job runs every 15 minutes and decides what is due at `now` (Brussels), the log is the persisted state, as in 0.3-2. No new table.
- **Preferences have no home for the channel switches and quiet hours.** `users` only has `lookahead_months`. Migration 0019 adds `notify_email` and `quiet_hours` (0018 is the push tables); the push switch of the Meldingen screen is "this device has a subscription".
- **The templates lack the "Meldingen aanpassen" link** (the layout comment says so) and the logo is text, not the board's PNG; the mail links to `/planning?groep=…` of the mockup do not exist (the real route is `/planning?maand=YYYY-MM#maanden` and Planning has no account parameter: 0.9-3 adds `rekening`).
- **The Meldingen screen offers an e-mail chip for `cat` and `contrib`**, which have no template; and the `joined` e-mail says the partner "linked the account at Argenta", true only for the IBAN-match join, not for an invitation join (0.8-0b).
- **Docs disagree**: `analysis/screens/emails.md` says nine templates (there are ten files), `meldingen.md` omits the Beveiliging group the mockup has, key names differ (`toestel` / `device`). Fixed in the analysis files with this refinement.
- **The reports engine is month-based** (`ReportMonths` groups by `substr(booking_date, 1, 7)`) and the web app has no week anywhere: a week needs a date-range variant of the same rule (0.9-3c step 1), not a second rule. The Kokonut printer's card is a fixed 30 rem high and clips a tall receipt, its paper stops a finger from scrolling the page, and its body is a flat list of floats: 0.9-3d adapts it.
- **iPhone detail**: the installed home-screen app has its own storage, so installing Saldo makes the phone sign in again and triggers a "new device" e-mail and push for your own phone. Accepted, written in the iPhone card ("Je wordt eenmaal opnieuw ingelogd").
- **The graph** (refreshed 18 Nov 2026) shows the dependency: `planning.Forecast` has three callers in `server` (forecast route, contributions, alerts), `sendLater` only the two sign-in handlers, `notify.Service` only `main.go`'s hourly job. 0.9 adds `notify → planning` and `notify → ledger`; `planning` and `ledger` never import `notify`.

## Known limits (document, do not solve in 0.9)
- **No per-type colour circle and no vector status-bar icon in a web push.** Android shows the app's own colour; Web Push takes a monochrome `badge` PNG and a large `icon` PNG. 0.9 ships a monochrome badge from `statusbar-icon.svg` and one `icon` per tone (green, ochre, red ring); the board's drawable is not reachable from a PWA.
- **The expandable chart is not built unless the spike allows it.** An `image` is fetched by the browser without cookies (a public or one-time URL carrying a person's balance forecast) and shows on the lock screen. Pushes open the app; the Planning screen has the chart.
- **iPhone shows title and line only, no image, may throttle**; e-mail stays the fallback (risk 19). A push to a subscription the OS revoked is removed on `404`/`410`.
- **Quiet hours are fixed** (22:00–07:00); editing the times is a later option.
- **The planning warnings use month ends** (0.8 decision 14); a dip on the 1st raises nothing.
- **A stale account does not warn.** An account whose newest data is older than 3 days gets no red/buffer message (the sync message covers it); manual current accounts always count.
- **A restore of an older database** loses the log: the next morning can repeat messages once. Documented in the backup notes.
- **Losing the VAPID key** (a database without the key) invalidates every subscription; the app re-subscribes on its next open (0.9-2 step 6), so the loss heals when each phone opens Saldo.
- **The 19:00 snapshot reads low.** At Sunday 19:00 and on the month's last day the last day or two are mostly pending, and reports leave pending out; the e-mail says "Stand zondag 22 nov, 19:00" and "Loopt nog". The in-app receipt is computed when opened and is complete once the bank has booked those days.
- **Weeks exist on the receipt page only**: Overzicht has no week period, so the week receipt has no "Open in Overzicht" (it links to the transactions of those dates).
- **The printer's physics is for a calm paper, not a long ledger**: a 45-line receipt prints in about 3 s (the feed speeds up for tall paper); on a phone the tear starts from a grab strip or a button, not from anywhere on the paper (so scrolling works).
- **Messages are sent per user from account-level facts**; two members of a shared account with different look-aheads can get a message on different days.
- **The digest ignores a backfill** (user decision 25 Nov 2026): linking a bank, or a joiner's fallback link, pulls in weeks of history with a source connection and no import batch. "Te categoriseren" counts a bank row only when its booking date is at most 7 days older than the day it arrived (`ledger.UncategorisedSince`, `fresh`), so the first evening after linking does not say "180 transacties"; what a bank posts a few days late still counts. Tested by `TestDigestIgnoresBackfill`.
- **A pending row that is booked in place after the digest mark moved past its id is never counted.** The mark is a row id (the highest id the digest counted) and a pending row keeps its id when the bank books it, so a row that was still pending while a digest counted newer rows lies below the mark when it is booked.
- **The plain-text part ends its footer after a bare `--` line**, as shipped in 0.2-4 and pinned by every golden; the RFC 3676 delimiter `-- ` (with a trailing space) is a later option.
- **The Dutch of the new mail copy is not reviewed.** The possessive in the manager mails ("Partners", "Annes", "Maries": a name ending in a silent e just gets an s) is unverified Dutch, and the copy of the types the design lacks (the shared invitation, the missing contribution, the digest, the manager variants, the week and month overviews) and the paper-style receipt block of the overviews have not been looked at in real mail clients (0.9-1 step 6, with 0.9-5).
- **Two push checks wait for a real iPhone** (spike additions of 0.9-2 step 8): whether Safari reports `applicationServerKey` on an existing subscription (the self-heal after a lost VAPID key assumes a match when it does not), and whether the `SameSite=Strict` session cookie travels on the service worker's `pushsubscriptionchange` PUT. Also open there: whether an iPad is detected as an iPhone-like device.
- **A different household member signing in on the same browser loses the previous person's push subscription** on the app's next start, by design: the browser remembers who switched push on (`saldo.push.user` in `localStorage`) and the app drops a subscription that belongs to someone else instead of inheriting it. The new person switches push on themselves.
- **The demo gets a stand-in device.** Demo mode has no device cookie, so each demo user gets one device, "Demo-toestel", the first time it subscribes; the fake sender records pushes and nothing arrives. The demo starts no notification jobs.
- **Push is unavailable without an https `public_url`.** `GET /api/push/key` answers `enabled: false`, and `PUT /api/push/subscription` and `POST /api/notifications/test` answer `503` "Pushmeldingen zijn niet beschikbaar: Saldo heeft een https-adres nodig." (demo mode is always enabled). E-mail is unaffected.

## Exit criteria
A forecast that turns red sends one push and one e-mail at 07:00 the next morning, and nothing again until the state changes or recovers and returns, on both phones; the lock screen shows no amounts or account names; the demo story over a simulated month gives exactly the expected messages; a signed-out device receives nothing; a user who switched the overviews on gets one week overview on Sunday at 19:00 and one month overview on the last day, each opening a receipt that prints with every category, subcategory and price, and nothing for an empty period or from before the upgrade.
